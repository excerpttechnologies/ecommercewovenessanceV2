# WhatsApp OTP login & payment notifications

Woven Essence uses **Meta WhatsApp Cloud API** as the single WhatsApp provider. There is no
Geeky Chat integration and no second provider. All credentials stay on the server.

## 1. Meta setup

1. Create a Meta app at <https://developers.facebook.com/> and add the **WhatsApp** product.
2. Register the business phone number and copy its **Phone number ID**.
3. Create a **permanent access token** (System User in Meta Business Manager) with
   `whatsapp_business_messaging` and `whatsapp_business_management`.
4. Add the credentials to the server environment (never to client code or git):

```
WHATSAPP_ACCESS_TOKEN=...
WHATSAPP_PHONE_NUMBER_ID=...
```

5. Set the template names after they are approved (see below).

No inbound webhook is required for OTP login or payment notifications.

## 2. Template approval requirements

Both messages must be submitted in **Meta WhatsApp Manager → Message templates** with the
correct category and language. Messaging to a customer who has not messaged the business first
is only allowed with an approved template.

### Authentication template (OTP)

- Category: **Authentication**
- Language must match the approved locale exactly, e.g. `en_US` (not `en`).
- Body variables are positional. This deployment uses two:
  `OTP Code: {{1}}. This is your OTP code for {{2}}. For your security, do not share this code.`
  where `{{1}}` is the 6-digit code and `{{2}}` is the purpose (`Login` by default).
- If the approved template has a **Copy code** button, set
  `WHATSAPP_OTP_INCLUDE_BUTTON=true`. Meta requires the OTP in both the body and the URL
  button parameter.
- Set `WHATSAPP_OTP_TEMPLATE` and `WHATSAPP_OTP_TEMPLATE_LANG`. If you use one shared
  language for both templates, `WHATSAPP_TEMPLATE_LANGUAGE` also works.

The code is never returned in an API response, written to logs, or placed in a Woven Essence
URL. The only URL containing it is Meta's `whatsapp.com/otp/code` copy-code button, which is
generated by the approved authentication template itself. For a body-only template, leave
`WHATSAPP_OTP_INCLUDE_BUTTON=false` and `WHATSAPP_OTP_BODY_PARAMS=1`.

> **Live template note (`wovenessence_otp`)**
> The currently approved template is `en_US`, has two body placeholders and a copy-code
> button. Its footer says “Expires in 1 minute” and its button URL is
> `...&code=otp{{1}}`. The app now accepts the 5-minute server TTL, but the footer should be
> updated to 5 minutes and the button URL changed to `...&code={{1}}` in WhatsApp Manager
> (then re-approved) so the copied value is the bare 6-digit code. The body always shows the
> correct code, so login still works without the copy button.

### Utility template (paid order)

- Category: **Utility**
- Body variables must be in the same order as `WHATSAPP_ORDER_TEMPLATE_PARAMS`.
- Default order used by the app:

```
Hello {{1}}! 👋

Thank you for shopping with Woven Essence!

Your payment has been successfully received.

🛍 Order Details:
Order Number: {{2}}
Order Date: {{3}}
Payment Method: {{4}}
Total Amount: ₹{{5}}
Payment Status: {{6}}
Payment Reference: {{7}}

We have successfully received your order.

Thank you for choosing Woven Essence!

For assistance, please contact our support team.
```

- Set `WHATSAPP_ORDER_TEMPLATE` and `WHATSAPP_ORDER_TEMPLATE_LANG`.
- Allowed parameter values for `WHATSAPP_ORDER_TEMPLATE_PARAMS`:
  `customerName`, `orderNumber`, `orderDate`, `paymentMethod`, `totalAmount`,
  `paymentStatus`, `paymentReference`, `orderStatus`.
- Amounts always come from the stored order (`netAmount`), never from the browser.

Template approval is controlled by Meta; the app cannot send until approval completes.

## 4. OTP login flow

1. Customer chooses **Login with WhatsApp OTP** below the existing email/password form.
2. Enters a country code (default `+91`) and mobile number.
3. `POST /api/v1/auth/otp/send`:
   - normalises the number and checks resend cooldown / mobile + IP rate limits;
   - generates a 6-digit code with `crypto.randomInt`;
   - stores only an HMAC-SHA256 hash with a 5-minute TTL;
   - sends the approved authentication template through Meta.
4. `POST /api/v1/auth/otp/verify`:
   - allows at most 5 incorrect attempts;
   - consumes the code atomically (a code cannot be reused);
   - looks up the existing customer by mobile;
   - for a new number, asks for a name first (no partial customer record), then creates the
     customer through the existing repository;
   - calls the existing `startCustomerSession`, so the existing JWT cookie, cart and wishlist
     are preserved. Guest cart/wishlist items are now adopted and merged into the customer's
     own lists instead of being deleted.

The OTP is never logged, returned in an API response, or placed in a Woven Essence URL.
Meta's `whatsapp.com/otp/code` copy-code button is the only URL that contains it, and that
URL is generated by the approved template. There is no development fallback that prints or
returns codes.

## 5. Payment-success notifications

`finalizePaidOrder()` is the single server-side payment-success point. It only sets
`paymentStatus = "Paid"` after:

- the checkout confirm step verifies the Razorpay signature and amount against the saved order, or
- the Razorpay webhook passes signature and amount checks.

After that atomic update, the app queues `queueOrderPaymentSuccessMessage(orderNo)` with
Next.js `after()`. A repeated confirm/webhook call for an already-paid order also queues it,
which safely acts as a retry.

Idempotency uses one `whatsappNotifications` row per order:

- unique key `order_paid:<orderNo>`;
- status `PENDING` while one attempt is in flight;
- status `SENT` + Meta message ID on success;
- status `FAILED` + sanitized reason on failure;
- a `SENT` row is never sent again, even from the admin retry button.

Transient network/timeout/HTTP 429/5xx failures are retried in the client. A delivery failure
never blocks or fails order processing or the webhook response.

The message is sent only for prepaid orders whose server-side status is `Paid`; COD orders do
not receive a payment-success message.

## 6. Admin

- **Order detail** shows the notification status, masked number, template, attempts, Meta
  message ID, sent time and failure reason. Paid orders without a successful message can be
  retried with **Send/Retry WhatsApp message**.
- **Settings → WhatsApp** shows readiness (credentials/OTP/order template), recent OTP
  deliveries and recent order notifications. It never shows the access token.
- Retry uses `POST /api/v1/admin/orders/:orderNo/ship` with `{ "action": "whatsapp" }`
  (`orders:write` permission).

## 7. Error handling

| Situation | Result |
| --- | --- |
| Invalid mobile number | `422 VALIDATION_ERROR` |
| WhatsApp number cannot receive the message | `422 WHATSAPP_DELIVERY_FAILED` |
| WhatsApp/template not configured | `503 WHATSAPP_OTP_UNAVAILABLE` / `WHATSAPP_UNAVAILABLE` |
| Resend too soon | `429 OTP_COOLDOWN` + retry seconds |
| Too many requests | `429 OTP_RATE_LIMITED` |
| Incorrect OTP | `401 OTP_INVALID` (up to 5 attempts) |
| Expired/reused OTP | `401 OTP_EXPIRED` |
| Attempt limit reached | `429 OTP_TOO_MANY_ATTEMPTS` |
| New number without a name | `422 REGISTRATION_REQUIRED` (code not consumed) |
| Order not paid | `409` from admin retry; automatic sends skip it |

### Diagnosing `503 WHATSAPP_UNAVAILABLE`

`WHATSAPP_UNAVAILABLE` means the request reached the Meta client but failed at the network
or provider level (timeout, DNS/TLS, HTTP 429, or HTTP 5xx). It does **not** mean the token or
template name is missing — those produce `WHATSAPP_OTP_UNAVAILABLE`. A provider 4xx (wrong
language, wrong parameter count, rejected recipient) produces
`422 WHATSAPP_DELIVERY_FAILED`.

The server now writes one sanitised line before mapping the error:

```
[whatsapp] OTP delivery failed {
  code, retryable, providerCode, httpStatus, providerSubcode,
  providerType, providerDetails, traceId, networkCode, reason
}
```

It never includes the access token, the OTP, or the customer number. Check the line and the
Meta template metadata:

```bash
# Phone number / credential check
curl "https://graph.facebook.com/v26.0/$WHATSAPP_PHONE_NUMBER_ID" \
  -H "Authorization: Bearer $WHATSAPP_ACCESS_TOKEN"

# Approved template shape (status, language, body variables, buttons)
curl "https://graph.facebook.com/v26.0/$WHATSAPP_BUSINESS_ACCOUNT_ID/message_templates?name=$WHATSAPP_OTP_TEMPLATE" \
  -H "Authorization: Bearer $WHATSAPP_ACCESS_TOKEN"
```

Common causes in this deployment:

- language sent as `en` while the approved template is `en_US`;
- one body parameter sent to a two-parameter template (or vice versa);
- a copy-code button template sent without its URL button parameter;
- `WHATSAPP_TIMEOUT_MS` unset. A previous bug treated a missing numeric value as `0`, so the
  effective timeout became its 1-second minimum; the config loader now uses documented
  defaults (10 s) and supports `WHATSAPP_REQUEST_TIMEOUT_MS`.

## 8. Testing

Automated tests cover phone normalisation, config defaults/legacy aliases, the exact Meta
template payload (language, two body parameters and the copy-code button), template parameter
order, payment-status gating and notification idempotency without contacting Meta. The OTP
send/verify persistence paths need a running MongoDB and are covered by the manual checklist
below. Live end-to-end delivery requires real Meta credentials and approved templates.

Manual checklist:

- existing email/password login still works;
- existing customer WhatsApp login;
- new customer: OTP verify asks for a name, then creates exactly one customer;
- incorrect code increments attempts; 5th wrong attempt locks the code;
- expired code is rejected; resend respects the cooldown;
- guest cart/wishlist survives OTP login;
- paid order sends one message; repeated webhooks do not duplicate;
- failed WhatsApp call leaves the order Paid and records a failure;
- admin retry sends after a transient failure and cannot resend a `SENT` message.
